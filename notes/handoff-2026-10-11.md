# Handoff: PowerA wired Xbox controller support on macOS

Written 2026-10-11 for a Claude Code session running on the owner's Mac with the controller plugged in. The research below was done without access to the device, so everything about this specific controller is unverified until Phase 1.

## Goal

Make a PowerA wired Xbox controller usable on macOS, ideally system-wide (visible to the Game Controller framework, browsers, and games), with rumble as a stretch goal.

The owner expects we will need to write our own driver. That may be true, but do not start there. The cheapest fix that works wins, and each phase below ends in a decision about whether the next one is needed.

## What we know

**Verified by research (sources at the end):**

- macOS 15 (Sequoia) and later ships a native driver for wired Xbox controllers that speaks Microsoft's GIP protocol (Game Input Protocol). So a first-party wired Xbox pad works out of the box.
- Third-party pads are not all covered. An SDL commit states that a number of third-party Xbox controllers are not supported by macOS but work through libusb with SDL's HIDAPI driver.
- SDL3 has a newer HIDAPI GIP driver (`SDL_hidapi_gip.c`) for wired Xbox One controllers, controlled by `SDL_JOYSTICK_HIDAPI_GIP`. libusb use is controlled by `SDL_HIDAPI_LIBUSB`.
- Linux xpad has PowerA-specific init quirks. Some PowerA pads send no input reports until they receive a rumble packet. A zero-intensity rumble works on some units; others need the real packet the Microsoft driver sends, followed by a zero rumble to stop the motors.
- 360Controller (the old kext) is dead on macOS 11+ and never supported PowerA or PDP pads after macOS 10.11.
- A DriverKit extension can present a virtual Xbox HID device on Apple Silicon (see thrustmacos). It needs SIP disabled for self-signed development builds and must be compiled as arm64e.
- Software USB capture on macOS (the `XHC20` interface trick) needs SIP disabled and is reported broken on macOS 15.6.1. Do not rely on it.

**Packet bytes from the xpad patches (verified from the patch text):**

| Purpose | Bytes | Notes |
|---|---|---|
| Power-on / start input | `05 20 00 01 00` | Required for pads with 2015+ firmware |
| PowerA rumble begin | `09 00 00 09 00 0F 00 00 1D 1D FF 00 00` | The packet the Microsoft driver sends |
| PowerA rumble end | `09 00 00 09 00 0F 00 00 00 00 00 00 00` | Stops the motors immediately |

Byte index 2 is a sequence number that xpad increments per outgoing packet. xpad applies the PowerA quirk to `24c6:541a`, `24c6:542a` and `24c6:543a`.

**From memory, verify before relying on it:**

- GIP devices expose a vendor-specific interface: class `0xFF`, subclass `0x47`, protocol `0xD0`, with one interrupt IN and one interrupt OUT endpoint.
- PowerA uses vendor IDs `0x24c6` and `0x20d6`.
- GIP input reports use command byte `0x20`; the guide button arrives as command `0x07`; the device announces itself with command `0x02` on connect.
- These pads run at USB full speed (12 Mbit/s).
- `libusb_detach_kernel_driver` on macOS needs root (or a special entitlement), so if Apple's driver has claimed the interface, the proof-of-concept scripts need `sudo`.

Check all of these against the current `xpad.c`, xone's `bus/protocol.c`, and SDL's `SDL_hidapi_gip.c` rather than trusting this list.

## Hard constraints

- **Do not change system security settings.** Disabling SIP, lowering Startup Security, and enabling system extension developer mode are the owner's call and the owner's hands. If a phase needs them, stop, explain exactly what is needed and why, and wait.
- **Ask before installing anything or running `sudo`.** List what you want to install and get a yes.
- **Do not write to the controller beyond the known init and rumble packets.** No firmware update commands, no fuzzing of the OUT endpoint.
- **Keep licences clean.** xpad and xone are GPL-2.0. SDL is zlib. Read all three for protocol facts; if we copy code, copy from SDL. The owner has not picked a licence for this project yet, so ask before importing anything.
- **Record everything.** Raw descriptors, captures and findings go in `notes/` so a later session can pick up without the device.

## Phase 1: Identify the device

```sh
system_profiler SPUSBDataType        # try SPUSBHostDataType if this is empty on newer macOS
ioreg -p IOUSB -l -w0
lsusb -v                             # from usbutils
hidutil list
```

Record in `notes/device.md`:

- Vendor ID, product ID, product string, bcdDevice, USB speed.
- Every interface: class, subclass, protocol, endpoints with direction, type, max packet size and interval.
- Which kernel or DriverKit driver, if any, has matched each interface (visible in the `ioreg` tree under the device).
- Whether the pad appears in System Settings > Game Controllers and at `https://hardwaretester.com/gamepad`.

**Decision:**

| Finding | Meaning | Next |
|---|---|---|
| Works in System Settings | Native driver handles it; the problem is app-specific | Find out which app fails and why; probably no driver needed |
| Interface is `FF/47/D0`, Apple driver attached, no input | GIP pad that the native driver fails to initialise. PowerA init quirk is the lead suspect | Phase 2 |
| Interface is `FF/47/D0`, no driver attached | Apple's driver does not match this ID | Phase 2 |
| Interface is `FF/5D/01` | Xbox 360 protocol (XInput), no native support at all | Phase 2 using xpad's 360 path instead of GIP |
| Plain HID interface | Not an Xbox-protocol device in this mode | Inspect the report descriptor; may only need a mapping |
| Not on the bus at all | Cable or port problem | Try a known data cable and a direct port |

## Phase 2: Userspace proof of concept

Goal: get input reports out of the pad from a script, with no driver work.

Write `tools/gip_probe.py` with pyusb:

1. Find the device by the IDs from Phase 1.
2. Detach any kernel driver from the controller interface and claim it.
3. Start a reader on the interrupt IN endpoint that hex-dumps every packet with a timestamp.
4. Log whatever the pad sends unprompted for two seconds (expect an announce packet).
5. Send the power-on packet. Log.
6. If there are still no input reports, send rumble begin then rumble end. Log.
7. Print decoded buttons and axes while the owner presses things.

Keep the init sequence as data (a list of packets), not code, so trying variants is quick. Save raw logs to `notes/captures/`.

In parallel, test SDL, since it may already solve the owner's actual use case:

```sh
git clone https://github.com/libsdl-org/SDL && cd SDL
cmake -B build -DSDL_TESTS=ON && cmake --build build -j
SDL_HIDAPI_LIBUSB=1 SDL_JOYSTICK_HIDAPI_GIP=1 ./build/test/testcontroller
```

**Decision:**

- SDL sees the pad and the owner only needs SDL or Steam games: stop here and document the environment variables.
- The probe gets reports: we know the working init sequence. Go to Phase 3.
- Nothing produces reports: go to "If we get stuck" below before writing more code.

## Phase 3: Pick the system-wide architecture

Ask the owner what "supported" has to mean (Steam only, browser, native Game Controller framework games, everything). Then choose:

**Option A: userspace daemon plus virtual HID gamepad.**
A launchd daemon owns the USB interface (libusb or IOUSBHost), runs the GIP init, and republishes input through a virtual HID device (CoreHID `HIDVirtualDevice` on macOS 15+, or `IOHIDUserDevice`). Fast to iterate on; no reboot cycle. The open question is the `com.apple.developer.hid.virtual.device` entitlement: test early whether a locally signed build can create the device on this machine with SIP on. If it cannot, Option A has the same SIP requirement as Option B and loses most of its advantage.

**Option B: DriverKit extension.**
A dext built on USBDriverKit matches the PowerA interface by vendor and product ID, subclasses `IOUserHIDDevice`, runs the init sequence in `Start`, and translates GIP input reports into HID reports. Entitlements: `com.apple.developer.driverkit`, `com.apple.developer.driverkit.transport.usb` (scoped to the vendor ID), and `com.apple.developer.driverkit.family.hid.device`. Development needs SIP off, `systemextensionsctl developer on`, and arm64e. Distribution to other Macs needs a paid Apple Developer account with those entitlements granted by Apple.

Either way, make the virtual device look like a controller macOS already understands: reuse the HID report descriptor and IDs of a first-party Xbox controller in Bluetooth mode so the Game Controller framework maps it without extra work. thrustmacos does exactly this and is the template to read first. A caveat to raise with the owner: borrowing Microsoft's vendor and product IDs is fine for personal use but not something to ship.

Recommend Option A if the entitlement test passes, Option B otherwise. Put the recommendation and the evidence in `notes/architecture.md` and get the owner's sign-off before Phase 4.

## Phase 4: Build

Suggested layout:

```
notes/            findings, descriptors, captures
tools/            gip_probe.py and other scripts
gip/              protocol core in plain C or Swift: init sequence, report parsing, rumble encoding
                  no OS dependencies, unit-tested against captures from Phase 2
bridge/           Option A daemon, or
driver/           Option B dext plus the host app that activates it
```

Order of work:

1. Protocol core with unit tests fed by recorded captures. This is the only part that is the same for both options.
2. Input only: sticks, triggers, d-pad, face buttons, bumpers, stick clicks, menu and view.
3. Verify in System Settings, the browser gamepad tester, and one real game.
4. Guide button, hot-plug, sleep and wake, two pads at once.
5. Rumble (HID output report to GIP rumble packet).

Useful while debugging a dext:

```sh
log stream --predicate 'sender == "<dext bundle id>"'
systemextensionsctl list
ioreg -l -w0 | grep -i -A20 <product string>
```

## If we get stuck

The fallback is a known-good trace from a host whose driver works, compared byte for byte against ours.

1. **Linux VM (free).** UTM with a Linux guest, pass the controller through, load `usbmon`, capture with Wireshark while xpad or xone drives the pad.
2. **Windows PC with USBPcap (free)**, if the owner has one. This shows what Microsoft's own driver sends.
3. **Hardware sniffer**, only if the VM passthrough itself misbehaves. Options the owner has already been given: Sipeed SLogic Combo 8 (about $15, 80M sampling, enough for full speed with sigrok's USB decoders), DSLogic U2Basic (about $67, 100MHz), or a Great Scott Gadgets Cynthion (about €209, a real protocol analyzer with Packetry). The two logic analyzers also need a USB pass-through breakout board to tap D+ and D−. The common 24MHz clones are too slow.

## Done means

- The pad shows up in System Settings > Game Controllers and all inputs register correctly in the browser tester.
- It survives unplug and replug, and sleep and wake, without a restart.
- `notes/` explains the device, the init sequence that works, and the architecture choice.
- A README covers build, install, and uninstall, including how to turn any security settings back on.

1. Exact PowerA model (the label on the back helps), and whether it is an Xbox One / Series pad or an older Xbox 360 one.
2. macOS version and whether the Mac is Apple Silicon.
3. Where the pad needs to work: Steam, a specific game, browsers, everything.
